# 標籤條碼檢查（純網頁版）

把標籤稿 PDF 拖進網頁，逐個條碼核對「條碼裡編碼的內容」與「條碼下方印刷的數字」是不是同一串。
**所有運算都在瀏覽器裡跑，檔案不會上傳到任何地方。**

> 為什麼需要這個：標籤是分批產生的，條碼與人眼可讀數字若在產生階段被打錯，
> 印出來之後兩者長得都很正常，只有掃描才看得出不一致。開印前要全檢，不能抽驗。

## 怎麼用

1. 開啟網頁：<https://pokaihsu1243-create.github.io/label-barcode-check/>
   （要離線用的話，雙擊資料夾裡的 **`離線啟動.bat`**，它會起一個只聽本機的小伺服器並自動開好瀏覽器。）
2. 填入「這份稿應該有幾個條碼」——**不填就不算數量已核對**：整批少印一個條碼，程式是看不出來的。
3. 把 PDF（或掃描／拍照的 TIFF／JPG／PNG，多頁 TIFF 會每一頁都掃）拖進去。
4. 看結論燈號 → 看逐列判定 → 用疊合對照圖自己複查一遍 →
   需要留底就按「列印／存成 PDF」，在印表機清單選「另存為 PDF」（版面已排成 A4 橫式）。

第一次開啟要下載約 24MB（程式相依 14MB＋辨識模型 10MB），之後瀏覽器會自己留著，不必重新下載
（清除瀏覽器資料、無痕視窗、換瀏覽器或換電腦會重新下載一次）。

**所有相依都放在 `vendor/` 自己託管，不連任何 CDN。** 工廠的電腦可能在防火牆後面、或裝了會擋外部網域的擴充套件，連得到 CDN 不能當作前提；自己託管也順便讓它在斷網時照樣能用。

> **不能用滑鼠雙擊 `index.html` 直接開。** 瀏覽器基於安全性，不允許 `file://` 的頁面載入 JS 模組，
> 程式會整個載不起來（畫面正常，但點了沒反應、拖了也沒反應）。所以才有上面那個 `離線啟動.bat`。
> 真的誤開了也不用猜——頁面會直接把原因和解法寫在畫面上。

## 判定怎麼來的

四條軌，其中兩條完全不經過 OCR：

| 軌 | 做什麼 | 經過 OCR？ |
|---|---|---|
| 條碼解碼 | zxing-cpp（wasm）解 Code 128 | 否 |
| OCR ×2 | 400dpi 與 800dpi 各獨立讀一次 | 是 |
| 字形覆核 | 全檔的字依形狀分群，同形狀的字互相佐證 | 票源是 OCR，**不算獨立證據** |
| 模板疊合比對 | 把 36 個候選字用 Arial 渲染出來比形狀，看最像哪一個 | 否 |

模板用的字形固定是 Arial（標籤稿的字形是固定的，不做成可選項）。對實稿 288 個字實測過：全部讀對，最吃緊的是 `0`（差距 0.040）與 `8`（0.041），都是門檻 0.02 的 2 倍以上；而 4 個印錯的字差距 0.29，等於 15 倍門檻——抓得非常明確。印刷品質若變差，`0`／`8` 會最先變得分不出來，那時候程式標 `?` 轉待確認，是安全的那一邊。

**OK 只給「有兩條互相獨立的證據支持」的列**，其餘一律標 CHECK 並寫明是哪一種不確定。

兩個解析度**一律都跑**，不是「讀不清楚才重試」——只在讀不清楚時才複查的話，
400dpi 讀錯但讀得很完整的那種列永遠不會被複查，等於只在對自己有利時才複查。
每一列都有**重試紀錄**可以展開：兩個解析度各讀到什麼、信心多少、模板比對讀到什麼、
哪幾個字是靠 800dpi 補上的、哪幾個字兩解析度讀不一樣（一律保留待確認，不挑一個用）、
以及最後依據什麼定案。800dpi 是真的重新渲染那一塊（不是把 400dpi 放大內插），
所以算得上新證據；輸入是影像時放大只是內插，程式不會拿它來把 CHECK 升級。

每一列都會把疑似錯字逐字標出來（例如「第 9 字：條碼為 9，OCR 為 8」），
**待確認的列也一樣**——那才是最需要人去看的。字數不一樣時會先做編輯距離對齊再比，
分成「換了字／OCR 缺字／OCR 多字」；OCR 只要漏掉開頭一個字，逐位比對會讓後面每個字
都錯位，變成列出一整排根本不存在的錯字，反而害人找錯地方。對齊本身不唯一時
（缺的字夾在一串相同的字裡、或兩邊差太多），就不硬指位置，改成「字數不同，位置可能偏移，
請人工確認」並把兩邊原文列出來。

對齊**只用於顯示**：不會去補改 OCR 原文，也不參與判定。

判定不確定時寧可叫人看，但也不會為了「看起來嚴謹」而亂叫——
警告多到變成雜訊，人就會開始無視真正的警告。

文字區會往左右抓得比條碼圖案寬很多，再依實際切出來的字收成「一整行」——
印字常常比圖案寬（QR 碼尤其明顯），抓不夠寬的話兩端會被切掉，
正確的標籤會被誤判成待確認。抓寬的同時以標籤外框（沒有外框就用與鄰居的中線）為界，
不會吃到隔壁標籤的字。

改了「應有條碼總數」之後，畫面上那份舊結果會被標成**「數量已變更，請重新核對」**
並淡化，避免把上一個數量下的「可以放行」誤當成新數量的結論。

## 對照圖

- **逐列疊合對照**：三條帶。①條碼解出的字疊在印字上 ②OCR 讀到的字疊在印字上 ③三排對位排列。
  紅框＝模板比對認定與條碼不符；橘框＝程式自己也不確定，請人眼複查。
- **原圖對照頁**：整頁原樣，在每個印刷數字正下方補上條碼解出的數字，
  **方向跟著標籤本身走**（原稿顛倒的，補上去的數字也跟著顛倒），可以在真實版面上用原本的閱讀方向再核一次。

## 為什麼 OCR 選 PP-OCRv3 而不是 Tesseract.js

在實稿上兩個都測過（每次 8 個條碼）：

| | PP-OCRv3 | Tesseract.js |
|---|---|---|
| 乾淨的稿 | 8/8 | 8/8 |
| 壓力測試（縮到 48%＋模糊 1.6px） | **8/8** | 7/8 |
| 再劣化一級 | 0/8 | 0/8 |
| 每張耗時 | **約 200ms** | 約 1170ms |

乾淨時兩者打平，劣化時 PP-OCR 多撐一級，而且快約 6 倍。
但真正決定性的理由是：**它就是桌面版用的同一個模型**，所以桌面版實測校準出來的門檻可以直接沿用。

移植過程踩到的兩個坑，都寫在程式的註解裡：

1. **文字必須先緊裁再送辨識**。連條碼下緣一起餵進去的話，文字在 48px 高的輸入裡只佔一半，
   CTC 會把相鄰相同的字併掉（`277` → `27`）。桌面版是靠 RapidOCR 內建的文字偵測自動達成。
2. **要做 Unicode NFKC**。模型字典同時收全形與半形，影像品質差時會輸出全形數字，
   不折半形就會被當成「跟條碼不一致」而誤報。

## 與桌面版的關係

桌面版（Python + RapidOCR + zxing-cpp）是本工具的來源，兩者用**同一個** PP-OCRv3 模型與
**同一個** zxing 引擎，判定規則與門檻也是照著移植的。在實稿上兩邊逐字比對過：
條碼內容、OCR 結果、字形覆核、模板比對、判定結果、標籤分組全部一致。

影像輸入也做了同樣的處理：EXIF 轉向照做、寬度不足 1600px 的圖先放大
（不放大的話數字只有十幾個畫素高，切不出字形，整份會變成一堆「待確認」）。

一個已知差異：**OCR 信心分數的尺度不同**。桌面版的分數來自 RapidOCR（偵測框的平均），
網頁版是自己算 CTC 各時間步的平均機率，同一張圖兩邊的數字不會一樣。
這個分數只在「信心低 **且** 沒有模板比對佐證」時才會改變判定，實務上模板比對幾乎都在，
所以影響很小——但它確實不是同一把尺，不要拿兩邊的分數互相比較。

另一個差異：桌面版可以用背景的 Edge 直接產生一個 .pdf 檔；網頁版沒有辦法自己寫檔，要在列印對話框選「另存為 PDF」。版面兩邊是一樣的。
